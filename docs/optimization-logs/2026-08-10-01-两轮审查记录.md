## 一、Bug 清单

按严重程度排列：

| 级别 | 位置 | 问题 | 影响 | 修复建议 |
|---|---|---|---|---|
| 🔴 严重 | `ask_svc_upgrade` / `cmd_upgrade` / `show_project_detail` 中的 `up_svc_ask:`、`up_svc_do:` 回调 | `callback_data` 有 **64 字节硬限制**，代码把项目名 + 服务名直接拼进去 | 项目名或服务名一长，确认按钮直接发送失败（`BadRequest`），功能不可用 | 改用短 ID：内存里维护 `id → (project, service)` 映射，回调只传短 ID；或按列表序号寻址 |
| 🔴 严重 | `cmd_prune` vs `do_prune` | 预览只列 **dangling（悬空）** 镜像，但实际执行的是 `docker image prune -a -f`，会删除**所有未被容器引用的镜像** | 用户确认的范围和实际删除范围不一致，可能误删旧版本镜像，且不可恢复 | 预览也统计"所有未使用镜像"，或去掉 `-a` 让动作与预览一致 |
| 🔴 严重 | `run_command_with_feedback` | 子进程**没有超时、没有取消机制** | `docker pull` 一旦卡在网络上，全局锁被永久占用，之后所有升级/清理全部被挡，`⏳` 消息永远不结束 | 加 `asyncio.wait_for` 超时，超时后 `terminate/kill` 子进程并解锁；最好附带"取消任务"按钮 |
| 🟠 中等 | `cmd_list` 按钮文字 | 按钮文本上限 **64 字符**，`f"{num}. {name} (多服务)"` 长项目名会超限 | 长名字项目按钮发送失败 | 截断显示（如 `name[:30]…`），或只显示短名 + 序号 |
| 🟠 中等 | `cmd_list` 主面板 | 项目多时文本无分页 | 超过 Telegram 单条消息 4096 字符上限，消息发送失败 | 分页（上一页/下一页/页码），每页 8~10 个项目 |
| 🟠 中等 | `do_upgrade_all` | 循环里不记录每个项目的成败，最后无条件提示"全部项目批量升级完成" | 实际有失败也显示成功，误导用户 | 统计成功/失败列表，汇总到最终消息 |
| 🟠 中等 | `cmd_prune` 的 dry-run | 没检查 `docker images` 的 returncode | docker 守护进程异常时，把错误文本当镜像列表展示，甚至弹出确认框 | 先校验 returncode，非 0 直接报错返回 |
| 🟠 中等 | `do_upgrade_project` 等所有入口 | `lock.locked()` 检查与 `async with lock` 获取之间存在竞态 | 快速连点两个按钮时，第二个可能静默排队后重复执行 | 进入函数直接尝试获取锁，拿不到就提示"忙"并返回 |
| 🟠 中等 | `_get_compose_projects_sync` | 只认 `docker compose`（v2 插件），无 `docker-compose`（v1）回退 | 老环境扫描结果为空 | 探测 `docker compose` / `docker-compose` 并选择可用者 |
| 🟡 轻微 | `global_error_handler` | `exc_info=context.error` 直接传异常对象，完整堆栈依赖 Python 3.11+（本机 3.11 实测 OK） | 3.8~3.10 上 traceback 会静默丢失 | 改成 `exc_info=True` |
| 🟡 轻微 | `_get_compose_projects_sync` | `json.loads(result.stdout)` 假定输出是单个 JSON 文档 | 若某些 Compose 版本输出 NDJSON（一行一个对象）会直接解析失败 | 逐行尝试解析，失败再整体解析 |
| 🟡 轻微 | `run_command_with_feedback` | `output_lines` 无界增长，实际只用到最后 30 行 | 大日志场景内存浪费 | 只保留最后 N 行（`deque(maxlen=…)`） |
| 🟡 轻微 | `button_handler` | `data.split(":", 2)` 没有防御畸形数据 | 脏数据触发 ValueError 进错误处理器 | 加长度/格式校验 |
| 🟡 轻微 | `check_permission` | 未授权用户也会收到回复 | 可被刷屏、被利用探测 bot 存在 | 可选：静默忽略或仅 log |
| 🟡 轻微 | `docker ps -a` 兜底 | status 硬编码为 `"running"` | 已退出的容器被显示为运行中 | 用容器的实际 status 字段 |
| 🟡 轻微 | `seen_dirs` 去重 | 同一目录下多个 compose 项目会被合并丢一个 | 边缘场景项目丢失 | 用 `name + dir` 联合去重 |
| 🟡 轻微 | 全局 | `import re` 未使用；`TokenMaskFilter` 在 root logger 和 handler 上重复添加 | 无害，仅整洁问题 | 清理 |

## 二、美化 / 体验规划

> 以下均为建议方向，未对代码做任何修改。

1. **主面板升级**：按状态分组（🟢 运行中 / 🟡 已停止），路径用等宽代码块，每项附服务数、运行时长、镜像版本；底部加磁盘占用统计。
2. **进度可视化**：升级时把同一条消息做成进度条（`▰▱▱▱`）+ 阶段标签（拉取 → 重建 → 完成）+ 已用时长，比现在堆日志更直观。
3. **分页导航**：项目多时用 `◀ 1/5 ▶` 翻页，按钮只放当前页，规避 4096 字符和按钮数量上限。
4. **确认页更清晰**：展示将要执行的具体命令、影响的服务清单，完成后对比升级前后的镜像 digest/tag。
5. **新增 `/status`**：一键查看所有项目的 `docker compose ps` 容器状态速览（含端口、健康状态）。
6. **运行中可取消**：任务进行时附"❌ 取消"按钮，配合超时机制真正中断子进程。
7. **清理功能细分**：区分"仅悬空镜像"和"所有未使用镜像"两个入口，预览时显示合计大小，再二次确认。
8. **统一视觉风格**：标题栏、分隔线、成功/失败卡片样式统一；失败时给出退出码 + 可执行的排查提示。
9. **审计日志文件化**：操作记录（时间、用户、命令、结果）写入 `RotatingFileHandler` 滚动日志，方便回溯。

---

## 三、结论

代码整体结构清晰，权限校验、全局锁、HTML 转义、日志脱敏这些基础做得不错。需要优先处理的是三个严重问题：

1. 回调数据超限（`callback_data` 64 字节限制导致按钮失效）；
2. prune 预览与实际执行范围不一致（可能误删镜像）；
3. 执行无超时/取消，导致全局锁被永久占用。

### 4.2 仍存在的问题

| 级别 | 位置 | 问题 | 影响 | 修复建议 |
|---|---|---|---|---|
| 🔴 严重 | `do_upgrade_all` + `run_command_with_feedback` | 取消只作用于当前一条命令，批量循环继续，且下一次调用开头会把 `_CANCEL_REQUESTED` 重置为 False | 用户点「🛑 中断执行」后批量仍会跑完，取消信号被静默吞掉，与按钮文案不符 | 循环内检查 `_CANCEL_REQUESTED` 后 break，汇总时标注「已中止」 |
| 🔴 严重 | `_CURRENT_PROCESS` / `_CANCEL_REQUESTED`（全局） | 取消状态是模块级全局变量，取消按钮 ID 未与具体任务绑定 | Bot 重启后旧进度消息上的取消按钮仍可点击，会误杀后续运行的其他任务 | 把进程引用存入取消回调 payload，仅当 ID 匹配时才 kill |
| 🟠 中等 | `do_upgrade_all` 汇总消息 | `success_list` / `fail_list` 直接 join 进 HTML，未 `html.escape` | 项目名含 `<`、`&` 时破坏排版甚至注入 | 逐项 `html.escape` |
| 🟠 中等 | 三个 `do_*` 入口 | `lock.locked()` 检查与 `async with lock` 之间仍有竞态（一轮第 8 条未修） | PTB 默认顺序处理下基本不触发；开启 `concurrent_updates` 后可能重复执行 | 合并「检查 + 获取」为原子操作（如受锁保护的 running 标志），或注明依赖默认顺序处理 |
| 🟠 中等 | `get_compose_projects` | 每次交互都全量扫描：`compose ls` + 每项目一次 `config --services` | 项目多时每次点击等待数秒 | 加 10~30s TTL 缓存，或并行扫描 |
| 🟠 中等 | `run_command_with_feedback` 实时预览 | compose 进度输出用 `\r` 而非换行，`readline()` 会阻塞到命令结束 | 预览不实时，用户看到「等待 → 突然完成」 | 加 `--progress plain` / `-q`，或按块读取 |
| 🟠 中等 | `ask_prune_confirm` | 未调用 `query.answer()` | 扫描期间按钮一直转圈 | 开头先 `await query.answer()` |
| 🟠 中等 | 超时 / 取消分支 | kill 后未 `await process.wait()`；`read_stream` 内 `process.kill()` 未包 try | 进程对象未回收；进程恰好退出时可能把「已取消」显示为「执行异常」 | kill 后补 wait，kill 包 try/except |
| 🟠 中等 | `_get_compose_projects_sync` | 多 compose 文件项目只取第一个 `ConfigFiles` 路径 | `-f a.yml -f b.yml` 且 b 非 override 时，服务列表与操作目录可能不准 | 解析完整文件列表，或文档注明限制 |
| 🟠 中等 | `_get_compose_projects_sync` | 无 `docker-compose` v1 回退（一轮第 9 条未修） | 老环境扫描结果为空 | 探测 `docker compose` / `docker-compose`（仅 v2 环境可忽略） |
| 🟡 轻微 | `button_handler` | 未知 / 无冒号 callback 静默放行且不 answer | 按钮转圈 | 加 `else` 兜底并 `query.answer()` |
| 🟡 轻微 | `TokenMaskFilter` | 只脱敏 `msg` / `args`，异常 traceback 中的 token 仍可能进日志 | 日志泄露风险 | 对 `exc_text` 一并处理 |
| 🟡 轻微 | 启动 / 工程 | 无 `/help`、无 `requirements.txt`；`ALLOWED_USER_IDS` 为空时无启动警告 | 部署排障不便，白名单为空时无人可用且无提示 | 补充命令与依赖清单，启动时校验并告警 |
| 🟡 轻微 | `run_command_with_feedback` | 进度条百分比为固定阶段值（30/80/90） | 不反映真实进度 | 按阶段 / 耗时动态更新（可选） |

### 4.3 二轮结论

一轮的三个严重问题已全部修复，整体可以上线。剩余问题中真正影响正确性的是取消语义（批量中止 + 取消与任务绑定）与批量汇总未转义；其次是扫描缓存、实时预览、`query.answer`、kill 收尾等体验与健壮性项。若保持 PTB 默认顺序处理，锁竞态可不做改动，但建议在代码里注明依赖。
